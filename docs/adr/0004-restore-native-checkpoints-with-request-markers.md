# Restore Codex Native Checkpoints with Host-only request markers

Status: **accepted** for replay; the replay-only creation state is superseded by [ADR 0005](0005-create-dual-checkpoints-inside-basic-manual-transactions.md).

An already durable Dual Checkpoint is restored by the ordinary `openai-codex` Adapter, not by a second compaction engine or a DSH core content type. The package declaration-merges `codex-native-checkpoint` into `@deepseek-ai/dsh-llm`'s `ContentBlockMap` and exports its versioned Host codec from `dsh-codex-auth/native-checkpoint`. The opaque JSON carrier records exact schema, codec and retention generations; provider/model provenance; a domain-separated account hash; a canonical compatibility digest; replay estimate and optional usage facts; and provider-owned canonical text-only retained-user Responses items ending in one opaque compaction item. Only those replacement items are forward-extensible. The enclosing schema is strict, lossless, bounded to 2 MiB, and rejects credentials, headers, raw turn state, request-local metadata, and unsafe object keys.

`CodexAuthAdapter` wraps both `super.prepareCall()`'s registration-bound stream and its direct `stream()` path. It clones checkpoint-bearing `GenerateOptions` and messages rather than mutating DSH's frozen call state. Every complete Basic-framed checkpoint with exactly one valid native block becomes a marker-only user message before pi-ai conversion; malformed mixtures become text-only Portable messages. An Adapter-owned `AsyncLocalStorage` scope carries the generated marker, candidate, Portable fallback, routed model, hashed account identity, and Adapter generation while each lazy stream iterator is advanced. It is request-local, collision-safe, cleared on iterator teardown, and never persisted or logged. Route generation replacement and plugin disposal invalidate old prepared/in-flight eligibility, so those calls use Portable while a later generation may still replay the unchanged durable candidate.

The plugin-owned pi-ai provider wrapper composes `onPayload` in a fixed order: provisionally restore every exact marker item, await callbacks that were already supplied, then re-evaluate compatibility against the effective final payload and materialize the corresponding representation at the same position. A finally compatible marker becomes cloned canonical native items; an incompatible marker becomes one ordinary Portable user item. A callback may change semantic controls, but may not erase/move the provisional checkpoint input, duplicate a representation, or make Native and Portable coexist. Missing, duplicate, embedded, leaked, or unconsumed generated markers fail before fetch, while ordinary marker-like text that was not generated for that request remains ordinary text.

Replay compatibility includes the exact provider, model, hashed Codex account, instructions, tool schema and policy, reasoning/text controls, service tier, and codec/retention generations. It excludes cache keys, request/session identifiers, headers, and Long Context Mode. The converter is pinned to DSH LLM and `dsh-llm-pi-ai` `0.1.2-alpha.5` plus pi-ai `0.84.4`; another installed pair strips the opaque block and delegates the Portable text. This exact runtime pin matches the tested prerelease baseline and leaves `cordis.patch.yml` unchanged. A final payload containing pi-ai's `additional_tools` history also uses Portable because that semantic input is outside the current digest.

DSH's compaction conversation projection is text-only: Portable summary blocks produce the visible compaction node. The custom block also carries `text: ''`, an empty generic-presentation sentinel that keeps alpha.5 Chat and Trajectory from JSON-stringifying its opaque `state`; a public published-client integration test renders both stock Conversation and Trajectory and proves the Portable text remains visible while the opaque bytes do not render. This does not remove the block from Session RPC or exports: it remains credential-free but sensitive ordinary Session data. The plugin's own public client `apply()` still registers exactly its settings and image views, with no conversation or custom-block renderer competing with stock presentation.
